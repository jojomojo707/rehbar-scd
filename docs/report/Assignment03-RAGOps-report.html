We extended the Assignment 02 RAHBAR pipeline (FAST-NUCES rules corpus, Chroma, FastAPI) with the data-management and testing lifecycle of the RAGOps paper. Ingestion now verifies every document, keeps a versioned data lake with quarantine and archive, and updates the index incrementally. A three-level test suite runs as a Kubernetes Job, gates a candidate change, and every query writes a reconstructable trace. All numbers below come from our own runs; the result files are under eval/results/a03/, traces/a03/ and docs/evidence/.

Thresholds (ConfigMap release-gate-thresholds): recall@5 drop ≤ 0.02 — with 27 answerable questions one lost gold page costs 0.037, so this allows no lost question; faithfulness ≥ 0.85 — the baseline judged 25/25 answers faithful, and with about 12 judged answers per run 0.85 tolerates one unsupported answer, a margin we keep because the judge was checked on only 10 hand labels; p95 ≤ 12 s — baseline p95 was 10.5 s (generation dominates, D3) plus about 15 % headroom; abstention correctness not lower than the baseline. Gate: candidate 384 PASS; TOP_K=1 REJECT (recall@5 0.500, a drop of 0.185), the eval Job ended Failed and it was never rolled out. Editing MAX_P95_SECONDS to 8 rejected the same candidate (p95 9.93 s) without a rebuild; restoring 12 passed again. Rescoring note: after the runs, five gold pages in the golden set were corrected (§2.7 is stored on page 12, not 13; §1.19 on page 9, not 8). Component metrics here are rescored from the saved per-question rows with the corrected pages (eval/rescore_component.py --golden), so they are higher than the job logs and screenshots, which show the scores at run time (TOP_K=1 at run time: recall@5 0.500 dropped 0.130 below the baseline 0.630 (allowed drop 0.020)). Both gate decisions are unchanged.

Release decision: released by the gate, then rolled back. The candidate passed the gate and was rolled out (kubectl set env deployment/api CHROMA_COLLECTION=rahbar-candidate, rollout status). Our live check found no benefit: retrieval was identical at document-page level (the handbook's clause-sized chunks are already under 384 tokens; mainly long annual-report chunks were split, 810 vs 764 chunks), faithfulness was slightly lower and the answer rate fell from 0.463 to 0.352. The answer rate is partly provider throttling (the TOP_K=1 candidate, which sends fewer tokens per question, answered 0.519), so we read it as "no evidence of improvement" rather than proof of harm. A change with no measured benefit and a possible cost should not stay live, so we treated it as a bad release and reversed it with kubectl rollout undo; the next trace shows collection rahbar-v20261125-120258 and embedding bge-small-en-v1.5@aa8f8b06/onnx-sha256:51f1bd0a, the previous versions. We repeated the release and undo on 27 Nov for the appendix screenshots; by then the live index was rahbar-v20261125-130024 (Batch A + B), and the trace after the undo shows that collection again. Lessons: add answer rate to the gate, and evaluate with a paid provider tier or paced runs so throttling does not mask real differences.

D. Observability

D1 each query writes one JSON line to stdout (kubectl logs) and to /pipeline-data/traces: trace id, timestamp, pod, query, rewrite, embedding model and version, collection and version, retrieved chunk ids with document, version, page, score and superseded flag, the same before the guardrail, filters, rerank order, full prompt and SHA-256, model parameters, response, citations, guardrail actions, injection flags, outcome, stage latencies and cache status. D2 eval/trace.py trace <id> prints the context and the rebuilt prompt and checks it against the stored hash. D3 baseline window (118 requests): top-1 similarity p10/p50/p90 = 0.6625/0.7559/0.859; abstention rate 0.6271; cache: bypassed by the suite on purpose (every question must reach retrieval and the LLM); stage p95 embedding 201.2 ms, retrieval 198.2 ms, generation 10779.1 ms; injection attempts flagged 8 (query rail). Cache window with normal traffic (2026-11-27, 18 requests: 8 questions, the same 8 again, 2 rewordings): hit rate 33% (6/18); every repeat of an answered question and one rewording hit, while abstentions and fallbacks are not cached by design, so their repeats missed; generation p95 2800.4 ms. D4 asking about e-mail passwords retrieved the injected Batch B chunk at rank 1 (0.86); the context rail removed the "SYSTEM NOTICE... ignore all previous instructions" sentences and the trace records context_injection_sentence_removed:it-acceptable-use-policy:00001; the answer stayed correct.

1. Query: what the 2026 handbook says about permitted absence and its consequence; outcome abstained, guardrail relevance_floor_abstention.

E. Coverage and drift

40 live-style queries (28 in the golden-set domain, 12 off-corpus). Threshold 0.7332 = midpoint of the highest unrelated-pair cosine (0.720) and the lowest paraphrase-pair cosine (0.747) of the module pairs: above it, a live query reads as "the same question in other words". Before: 19/40 = 47.5% (in-domain 18/28, off-corpus 1/12), below the paper's 85 % → exit 1. Uncovered topics: attendance (4), academic warning (2), library, library fines, scholarship, semester calendar, and the off-corpus topics healthcare (2), transport, food, parking, employment, sports, finance, weather, technology, travel. E4: 15 new questions (7 answerable/hard, 8 must-abstain) → 37/40 = 92.5%, exit 0; still uncovered: pharmacy, laptop BIOS, visas.

E3 drift (Batch B ingested, suite re-run on all 47 questions, compared on the 32 shared with the baseline): recall@5 0.6852 → 0.9074, MRR 0.6235 → 0.821, nDCG@5 0.6287 → 0.8324; answer rate 0.463 → 0.7037, faithfulness 1 → 0.9474, p95 10.51 → 3.901 s; module unchanged; gate PASS. Why: the six Batch B questions became answerable once their documents were indexed; nothing in Batch A moved (Batch B adds 18 chunks to 764). The entrepreneurship policy's current version changed to the revision, and the injected document is now retrievable (handled by D4). The one unfaithful answer (H05) claimed the older attempt stays on the transcript, which no retrieved passage says; the judge caught it. Fallbacks on the shared questions: 7 → 4; the provider's daily token limit (200,000) was reached again only on the last six E4 questions (E402–E407), which affects the 47-question totals, not this comparison. A first rerun at 13:04 UTC hit the daily limit throughout and is kept as 20261125T130413Z-drift-batch-b (not used).

4. Short answers

  1. Most catches and the miss. In Batch B, completeness and uniqueness each caught three documents (missing title/version, truncated text, corrupt PDF; two exact copies and one near-copy at 0.998), quality one (the corrupt PDF also failed extraction). Nothing caught the injected instruction: it is well-formed, unique, current text. A content check at verification (the API's injection patterns or a prompt-guard classifier, e.g. Llama Prompt Guard) should flag it for human review. The paper's consistency check (contradictions) is also missing.
  2. Module fine, end-to-end not. In C1 the embedding module and retrieval component were identical for baseline and candidate (gap 0.302, recall@5 0.685), yet the candidate's answer rate fell from 0.463 to 0.352 and faithfulness from 1.000 to 0.958. The baseline shows it too: a 0.302 module gap, but H03 abstained although its gold chunk was retrieved (D5).
  3. Archive or delete. We archive: superseded, replaced and deleted versions move to archive/<doc_id>/<version> and stay in the manifest; superseded versions stay indexed with superseded=true and are filtered out of normal retrieval. Deleting would break rollback (no --restore-version), version questions such as V01 on the Aug-2023 rules, and audit of old answers whose traces cite the old document version.
  4. Least trusted metric. Faithfulness: the judge (gpt-oss-120b) is from the generator's model family, the denominator is small (about 12 answered questions per run) and rate-limit fallbacks change which questions get answered. p95 latency is the second: it includes provider retries under the 8,000 tokens-per-minute limit.
  5. Hardest idea and our changes. Testing against evolving data with a stable baseline: Batch B questions are unanswerable until Batch B is ingested, so we keep them in the set and compare runs on shared question ids. We changed: a recency failure archives the older version instead of quarantining it (the paper archives and replaces); superseded versions stay indexed behind a metadata filter; the coverage threshold is derived from module pairs; live testing is a gated candidate Deployment plus rolling release instead of shadow or A/B traffic.
  6. Kubernetes responsibilities. Single writer: only the indexer image contains write code, and it runs only as the ingestion Job indexer, its CronJob reindex (concurrencyPolicy Forbid) and Job candidate-ingest (the same ingestion code with the candidate ConfigMap, writing only rahbar-candidate-* collections), all under service account rahbar-indexer; the API only reads. Ingest + verify + lake + retrieval sources: that Job and PVC pipeline-data. Offline testing and gate: Job eval + ConfigMaps release-gate-thresholds and eval-target. Live testing and release: Deployment api-candidate + Service + NetworkPolicy (only evaluation pods reach it), Deployment api RollingUpdate and rollout undo. Reliability: requests/limits, HPA, StatefulSet + PVC for Chroma. Secret rahbar-secret holds the LLM key.
