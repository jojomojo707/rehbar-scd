# hpa-startup-scaling.txt: Engineering Note Q3. The CPU HPA scales on start-up work, not on load.
# 2026-11-06T20:04:08Z, minikube (4 CPUs, 8 GiB), namespace rahbar, dev overlay, real index (764 chunks).
# Clock check: laptop date -u = 20:04:08; minikube node date -u = 20:04:09.
# Context: the api Deployment was rolled six times between 19:40 and 20:00 UTC for failure-analysis
# stages C and E (new ReplicaSets created at 19:40:32, 19:42:31, 19:45:11, 19:51:48, 19:55:56 and
# 19:59:41; `kubectl get rs -l app.kubernetes.io/name=api`). The only traffic was the 18-question
# golden eval, run sequentially (one request at a time), plus 3 single questions. Each new pod
# loads the fastembed model (BAAI/bge-small-en-v1.5) and warms Chroma at start-up, which burns
# CPU for tens of seconds. The HPA divides that by the 250m request and scales up; it then
# scales down only after the 300 s stabilization window. Nothing about real demand changed.
